# Local OpenBin AI analysis implementation plan

> **For agentic workers:** Use superpowers:subagent-driven-development for the independent adapter/UI tasks; parent integrates queue, migrations, runtime and acceptance. Preserve this ledger.

**Goal:** Run actual local model inference on OpenBin/Ghidra evidence, produce owner-private evidence-linked malware triage reports, and expose queued progress, cancellation, history, export and completion alerts.

**Architecture:** Existing network-isolated Ghidra worker decompiles an uploaded native Windows EXE/DLL. A bounded local worker holds input bytes only in memory, feeds selected decompiled evidence to a loopback-only model, validates evidence citations, and stores report metadata/results. No sample execution, cloud model calls, provider quota or raw-upload persistence. In-flight jobs are interrupted after server restart; users must resubmit because sample bytes are deliberately not persisted.

**Tech stack:** Flask/SQLite schema 5, existing Docker/WSL OpenBin worker, local Ollama API and Qwen3 4B CPU model, vanilla JS/Jinja. Hardware observed: i7-5600U, 16 GiB RAM, Intel HD5500, Windows 11; D: has ~14 GiB free and C: ~120 MiB. Model/runtime assets must be on D:.

**Spec:** User approved the previously listed local AI model/integration/workflow/results/jobs/evaluation work with “so do that.” Earlier opt-out of design questions persists. No paid provider keys are required; the OpenAI credential gate does not apply to this explicitly local inference path.

## Rulings and scope

- The downloaded BINNY entry point requires OpenBin authentication and is an interactive terminal application. Reuse the official OpenBin Ghidra extraction plus a local constrained inference adapter instead of invoking its cloud-authenticated CLI from the web request. Report the actual pipeline, never claim BINNY ran. A future full agent harness is optional.
- Use an existing pretrained model; do not invent a trained classifier or measured accuracy. Deliver an evaluation harness/protocol and inert-fixture/local inference acceptance. A defensible malware accuracy benchmark requires independently labeled authorized samples; absent data is a reported limitation, not fabricated completion.
- One job processes at a time; at most three outstanding requests. Uploads remain memory-only (10 MiB max). Metadata/report persist with owner access controls. Restart/cancel/failure never yields a safe verdict. Model evidence is bounded and coverage is explicit.
- Model calls are loopback-only, no proxy/redirect/cloud fallback, tools or sample execution. Treat all decompiled strings as untrusted input and validate citations against the exact evidence given. Findings without valid evidence cannot become confirmed results. Verdicts: suspicious, no_indicators, inconclusive; no probability claims.
- Existing key/document/provider features remain unchanged. Schema 4→5 is additive with verified pre-upgrade SQLite backup. Restore must accept 2/3/4/5 and create the new table for old backups.
- Keep current working directory because the parent repository has no Git HEAD; use the current source ZIP as baseline. Do not delete user files or perform unrelated git operations.

## Interfaces and ownership

1. Parent owns models.py (AIAnalysis), database.py/operations.py migration/restore, new ai.py routes, ai_jobs.py worker and inference process boundary, registration/startup, intelligence feed integration, runtime installer/start scripts, docs and integration verification.
2. Adapter implementer owns local_ai.py and tests/test_local_ai.py only. `analyze_decompilation(decompiled, sha256, config, cancel_event=None, on_progress=None) -> dict`; config keys LOCAL_AI_URL (default http://127.0.0.1:11434), LOCAL_AI_MODEL (qwen3:4b), LOCAL_AI_TIMEOUT (600). `model_status(config) -> dict` returns available, model and message without making inference. Output includes verdict, summary, findings, coverage, limitations, model, model_digest, ai_model_ran=true, processing_location=local. Evidence IDs and literal source quotes must validate. No arbitrary tool execution.
3. UI implementer owns new ai_workspace.html, ai_detail.html, ai_history.html, ai.css, ai.js; base.html navigation; analysis_updates.html and analysis-updates.js needed for AI links/watch integration; tests client UI as needed. Route endpoints: ai.workspace (/ai GET/POST), ai.detail (/ai/<job_id> GET), ai.status (/ai/<job_id>/status GET JSON), ai.cancel (POST), ai.export (GET JSON), ai.report (GET PDF), ai.history (/ai/history GET), ai.delete (POST terminal only). Job object fields: id, filename, sha256, size, state, stage, progress (milestone not measured crypto%), model, result(dict), error, created_at, updated_at. Workspace context jobs (latest 5), availability (available/model/message). Detail context job. History context pagination. Job states queued/running/complete/failed/cancelled/interrupted; stage queued/inspecting/decompiling/analysing/validating/complete etc. Status returns id/state/stage/progress/error/result_url; GET polling does not extend idle session. Form upload name=file and trusted_server=on required. Notification feed exposes AI rows as kind=local_ai and URL=/ai/<UUID>, with queued/running or complete/failed (cancelled/interrupted label remains truthful), watch_ai parameter.
